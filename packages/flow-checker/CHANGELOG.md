# Changelog

## Unreleased

- **Requests after an early exit.** A request a shared helper sends only after an early `return` or `throw` didn't happen (for example a token refresh and retry after `if (res.status !== 401) return res`) is now marked `conditional` ("sometimes"), like one inside an `if`. Before, each method of a catch-all proxy listed the refresh as part of its chain.

## 0.2.2

New Components and Requests screens, plus fixes found by running 0.2.1 on a large real app (54 pages, a catch-all proxy route, react-hook-form forms, custom React Query hooks). Models saved by 0.2 still load.

On that app: things to check 129 → 15, unknown triggers 64 → 8, unresolved URLs 35 → 2, `model.json` 24.5 MB → 7.6 MB, and the largest page view 68,000 → 14,000 DOM nodes. On a second app, 32 of 46 earlier captures now match a request site (0 before), with 2 ambiguous (8 before).

- **Components and Requests screens.** The dashboard has two new screens, also in the static HTML export. The Overview's Components and Requests cards now open them.
  - **Components:** every component, searchable by name or file, filtered by kind (server / client / shared) and by what it has (sends requests, things to check, not on any page), and sorted by name, requests or pages.
  - **Requests:** every request, searchable by URL, component or file, filtered by when it is sent (on load, on events, server-side, unknown trigger), status, transport and flags. The same request sent from several places is one row.
  - The selected item opens beside the list, and the filters stay in the URL.
  - Each part of the cards' detail line (`117 server`, `106 on events`...) opens the matching filtered list. The Requests card also counts requests with an unknown trigger.
- Links to a request (the overview's to-do list, Live, flows, the GraphQL / tRPC / SSE / WebSocket / Postman sections) open the request on its own instead of the component that sends it.
- **Server hook placement.** The flow-checker blocks must be the first statements of `register()` in `instrumentation.ts`, outside any `if`. Pasted inside an existing condition (`if (process.env.NODE_ENV === 'production')`), they never ran under `next dev` and server capture silently stayed off.
  - `doctor` now reads `register()` (a function, an arrow or function expression, `export { setup as register }`, or a re-export from another project file) and fails when a block is inside an `if` / `else`, `switch`, loop, `try`, a ternary or `&&`, a nested callback, after other code or an early `return`, or when `register` isn't `async`. It names the line and prints the lines to move. Each block (Node.js and edge) is checked on its own.
  - `init` edits an existing `register()` instead of asking you to: it puts the blocks first, makes `register` `async` when needed (`void` becomes `Promise<void>`), gives an `() => init()` arrow a body, and moves misplaced blocks when run again. Shapes it can't edit (a re-export from another file) still get a note.
  - `dev` warns at start when the server hook is misplaced, and again, once, when your app answers route handlers that send requests but no server-side request is captured within 10 s. Live shows the same warning as a banner.
- **Dashboard on large apps.**
  - Lists that grow with the app show five entries, then "+N more": the queries a cache call hits, cache calls, where a page leads, route handler callers, layout requests and where a type is used. A cache call with no key reads "→ every query". Request details are only rendered when opened. A page that listed about 120 queries per cache call (about 44,700 DOM nodes) now stays small.
  - A new screen opens at the top instead of at the previous screen's scroll position. Back and forward return to where you were; search boxes and toggles keep the position.
  - Route handler pages list the requests the handler sends first, then its callers grouped by the URL they send (the concrete paths for a catch-all handler like `/api/[...path]`), with callers on the same line folded into one row and a search box. The Overview's Route handlers card opens a list of route handlers.
  - Types: instantiations of a generic (`Page<User>`, `Page<Post>`) fold into one row, and unused types are behind a "Show unused" toggle.
  - A navigation in a shared hook is one row "from N components" instead of one per component.
- **React Query keys.**
  - Enum members (`[QueryKeys.feed]`, also `const enum`, imported or re-exported), `as const` object properties and `const` strings are read as fixed key segments, also inside template literals. Before, an enum member was read as a runtime value (`[:feed]`).
  - A key segment the scan can't read (a value from a package, a module value it can't follow) is shown as `?name` and is never treated as "any value": a cache call whose key starts with one (or with a runtime value) says "key not known" instead of hitting every query in the app, and one with a known start links by that start only.
  - Keys and query functions passed to your own query hooks (`useList({ queryKey, queryFn })` calling `useInfiniteQuery`, with destructured, spread or positional arguments) are followed per call: each call is its own query site with its key, instead of a plain `fetch`, so invalidations of that key find it.
  - Components that mount the same query (same key and query function) share one request. Its capture now verifies all of them (`+N shared` on Live) instead of being ambiguous.
- **What starts a request.** Fewer `unknown` and wrong `page-load` triggers:
  - A handler passed through a call is followed to the event prop it ends in: `onSubmit={form.handleSubmit(onSubmit)}`, `const submit = handleSubmit(save)`, `debounce(search)` kept in a variable, your own wrappers (`withGuard(remove)`), and options of a form hook (`useFormik({ onSubmit })`, whose `handleSubmit` goes to the form). Functions passed by reference (`handleSubmit(save)` with `save` imported, `useEffect(load, [])`) are now walked too.
  - A callback handed to your own hook (`useSubmit({ onSubmit: verify })`) runs where the hook's result is used.
  - `on*` entries of object configs (`{ label: 'Export', onSelect: exportAll }`) are events.
  - A function shared through a context (`<Ctx.Provider value={{ remove: mutation.mutate }}>`, also through `useMemo` and React 19's `<Ctx value>`) is placed where the consumers (`useContext(Ctx)`, or a hook that returns it) use it.
  - A hook that returns several mutations gives each caller only the ones it uses: `const { remove } = useItems()` no longer lists `add` and `update` with an unknown trigger. A result passed on whole keeps them all.
  - A local function used as a `mutationFn` / `queryFn` is one site through its hook, not also a second site without it (sometimes with a `page-load` trigger).
- **URLs.**
  - `new URL()` is read through `.href`, `.toString()`, `String()` and templates, and its base can be an env value or a constant (`new URL('/v1/x', process.env.API_URL)` → `{API_URL}/v1/x`), not only a string.
  - `.replace()` (strings and regexes), `.replaceAll()` and `.slice(n)` with known arguments are applied.
  - A URL read from data at runtime (`fetch(file.url)` after `res.json()`, `files.map((f) => fetch(f.downloadUrl))`) is information ("URL from the data", `runtime-url`), not a "could not be resolved" warning. A URL from a prop is still a warning: the parent decides it.
  - **Catch-all proxies.** A route handler like `/api/[...path]` that forwards the incoming path (`params.path.join('/')`, `request.nextUrl.pathname`, `new URL(request.url).pathname`, with `.replace()` or `.slice()`) sends to `{API_URL}/:path*`, and each request to it shows where it goes: `POST /api/reviews` is forwarded to `{API_URL}/reviews`. `[[...path]]` works too.
  - A request a shared helper sends only sometimes before the real one (a token refresh) is marked `conditional` and shown apart ("Sometimes also on the server"), not as part of every chain.
- **Components chosen at runtime.** `const Comp = asChild ? Slot : 'button'`, nested ternaries, `cond && A` and lookups in a constant record (`ICONS[name]`) list each project component they can be, as conditional children. When every choice is a library component or an HTML tag, it is one external child with no warning.
- **Library types.** A package's own object types (react-hook-form's `Control<T>`, a carousel API) are kept by name instead of being expanded down to `Window`, plain values (`string`, `boolean`, literals) are shown at any depth, and a library type's arguments no longer make a type "partly resolved".
- **Flows from layouts.** A flow that starts in a component a layout renders (a search bar in a header) shows on every page under that layout.
- `.flow-checker/model.json` is now version 11. Version 1–10 files still load.

## 0.2.1

Fixes found by running 0.2.0 on a large real app (a 54-page Next.js 16 app with its own `request()` wrapper). Models saved by 0.2 still load.

- **URLs through helpers.** A URL built by a project function (`proxyUrl(endpoint)`) is followed into it, including ternaries the scan can decide (`AUTH_ENDPOINTS.includes(endpoint) ? '/api/auth…' : '/api…'`, `===` checks, `url.includes('?')`), `.toUpperCase()` / `.toLowerCase()` / `.trim()`, and helpers that add an optional query (`withCursor(url, cursor)` with several returns, `cursor ? '/x?cursor=…' : '/x'`). On that app, unresolved URLs went from 728 of 857 sites to 35.
- **One site per call through a wrapper.** When a call into a wrapper reaches `fetch` on several branches (a multipart branch and the normal one) and they send the same request, it is one site: the branch not guarded by an `if` is kept. Duplicate sites (and their warnings) are gone.
- **Mutation triggers through custom hooks.** `mutate` / `mutateAsync` handed out by a custom hook (`return { save: mutation.mutate }`, inside a returned `useCallback`, or wrapped as `guard(mutation.mutate)`) is followed to where the hook's caller uses it. A mutation is never a page-load request: one that can't be placed is `unknown`. Router calls and requests in a function a custom hook returns are placed the same way.
- **Components.** Aliases of library components (`const Form = FormProvider`, `const Dialog = DialogPrimitive.Root`) are external; compound components (`Card.Header = CardHeader`, or `{ Header: CardHeader }`) resolve to their component; a component passed in as a prop (`({ as: Tag }) => <Tag />`) is a new `prop` reference instead of "could not be traced".
- **Matching.** Stack frames in code many sites share (the app's request helper) count for little, so a site with an unknown URL no longer wins on them alone. A request another site's script sends to its own servers (a Google sign-in SDK) is marked `third-party` instead of "the scanner probably missed it", and left out of the unmatched count and of recorded flows.
- **Dashboard.**
  - The overview lists one note per request with everything the scan couldn't resolve about it.
  - Pages show where they redirect while rendering ("Leaves this page", with the pages a pattern can go to). They keep their own requests apart from those their layouts send on every page, and fold the same request sent from several places into one row that says where from.
  - The route map lays out many sibling pages in a grid of columns by route group, opens at a readable zoom, counts each page's own components, drops the stacked edge labels, and hides layout links and middleware redirects behind a toggle.
  - Live: server hops show which feature they were made for (`LatestPosts › GET /api/[...proxy]`), and the toolbar wraps instead of running into the side panel.
  - Recorded flows put the page load first and are named after the pages they went through when no name is given. An unwalked flow says "not walked yet". The route tree leaves out folders with no route files.
- **React Query keys on the first request.** The browser runtime found the app's `QueryClient` through the copy of React's tree saved on the root, which is empty right after React's first commit. A query that sent its request then lost its key (seen on Next 13.4 on macOS). It now searches the tree on screen.
- `.flow-checker/model.json` is now version 9. Version 1–8 files still load.

## 0.2.0

React Query in depth, middleware, Postman collections as the API contract, tRPC, GraphQL, server-sent events and WebSockets, plus progress output for every command. Models saved by 0.1 still load.

- **Progress output for every command.** `dev`, `scan`, `export`, `init` and `doctor` no longer look stuck on large projects: in a terminal a live line shows a spinner, a progress bar for the whole command, the current step with its count and time, and each scan phase leaves a `✓` line (files loaded, routes, components, requests, flows). `dev` also shows starting the dashboard and waiting for your app's port until it is ready, and re-scans show a short progress line. `doctor` prints each check as it runs. Plain lines in CI and piped output.
- **`--verbose`** prints the resolved config and where the scan runs; **`-q, --quiet`** turns progress output off.
- `scan` and `export` scan in a worker thread, like `dev`.
- **React Query, in depth (v4 and v5).** Query keys are read into segments (`['todos', 'detail', :id]`) through key factories, `queryOptions()` and functions that return options. New: `useQueries` / `useSuspenseQueries` (one request per entry), `usePrefetchQuery`, `queryClient.fetchQuery` / `prefetchQuery` / `ensureQueryData` / infinite variants, and v4's positional `useQuery(key, fn)` / `useMutation(fn, options)`.
- **Query cache links.** `invalidateQueries`, `refetchQueries`, `resetQueries`, `removeQueries` and `setQueryData` are linked to the queries their key hits (by prefix or `exact`), and to the mutation whose callback calls them. A server-side `prefetchQuery` handed over with `HydrationBoundary` (or v4 `Hydrate`) is linked to the client query it fills. Shown on request and page views, in flows (as steps after the mutation), in `scan --requests` and in the Markdown export.
- **Captures know their query.** In the browser, each request sent by a React Query query or mutation carries its key (redacted like bodies), and the matcher uses it (`query key` evidence).
- **Middleware (`middleware.ts`, and `proxy.ts` on Next.js 16).** The scan reads `config.matcher` (strings, `has` / `missing` objects, constants) and works out which pages and route handlers it runs on; each page shows it in the dashboard and the Markdown export (new `middleware.md`). `NextResponse.redirect()` / `Response.redirect()` become redirect edges on the route map, with the pages they can fire on and the condition around them (`if !token`); `NextResponse.rewrite()` is recorded and used to resolve captured URLs (and links) to the page that answers them, as is the default locale of next-intl's `createMiddleware()`. Requests sent from middleware get a `middleware` trigger.
- **Middleware capture.** On Node.js (Next.js 16 `proxy.ts`) its requests are captured with the incoming request, and matched with new `middleware` evidence (its matcher and the stack). On the edge runtime (`middleware.ts` before 16) a new edge hook (`@integr8-media/flow-checker/runtime/edge`) captures `fetch`, best effort. `init` adds it; `doctor` checks it and warns about `proxy.ts` before Next.js 16.
- `new URL('/path', request.url)` resolves to `/path` in request and redirect URLs.
- **Postman collections as the API contract.** Point `postman` in the config at a v2.1 JSON export, a git-native v3 YAML collection folder or a cloud collection (`{ id, apiKeyEnv }`, key read from an env variable and never stored), with an optional environment for `{{variables}}`. Every scan matches request sites to collection requests by method and URL, flags requests the collection doesn't have (`not in collection`) and collection requests nothing calls (`unused endpoint`), fills missing response and body types from saved examples (and type-checks captures against them), flags code types that don't fit the examples (`contract mismatch`), and fills URLs the scan couldn't resolve from the one request the call's names and method point to. New command `flow-checker postman import` (also `--collection`, `--environment`, `--api-key-env`); the import is cached in `.flow-checker/postman/` (gitignored). Shown on the dashboard overview and request views, in `postman.md` of the Markdown export, and checked by `doctor`.
- **tRPC (v10 and v11).** Procedure calls are request sites: `createTRPCReact` hooks (`trpc.todo.byId.useQuery()`, `useMutation`, `useInfiniteQuery`, ...), the vanilla client (`client.todo.add.mutate()`), `utils.todo.byId.fetch()` and v11's `useTRPC()` options with React Query (`useQuery(trpc.todo.byId.queryOptions(input))`, `useMutation(trpc.todo.add.mutationOptions({ onSuccess }))`). The router is read from the route handler's `fetchRequestHandler()` (or the client's `AppRouter` type): routers, merged routers and v11 plain objects, with each procedure's input type (from `.input()` zod schemas) and output type (`.output()`, else what the resolver returns), so calls are typed without annotations. Requests a procedure's resolver sends are its next hop. `utils.todo.invalidate()`, `trpc.todo.list.pathFilter()` and `queryKey()` become cache links to the procedures they hit. New `tRPC` section on the overview, a tRPC row on requests, `trpc.md` in the Markdown export.
- **tRPC capture.** A batched request (`/api/trpc/a,b?batch=1`, also streamed by `httpBatchStreamLink`) is split into one capture per procedure, with its own input, result or error and status, so each is matched (new `tRPC procedure` evidence) and type-checked on its own. superjson-wrapped values are unwrapped. Server requests made while a batch ran are tied to the procedure they belong to.
- A response body the app stops reading early (tRPC's stream link aborts the request once it has every result) is kept as far as it arrived instead of being dropped.
- **GraphQL (Apollo Client 3 and 4, urql, Relay).** Operations are request sites, by name and type: Apollo's `useQuery`, `useSuspenseQuery`, `useBackgroundQuery`, `useLazyQuery` (sent where the function it returns is called), `useMutation` (with `onCompleted` / `onError` followed for navigation) and `client.query()` / `mutate()`; urql's `useQuery({ query })`, `useMutation()` and `client.query()`; Relay's `useLazyLoadQuery`, `useQueryLoader` (sent where `loadQuery` runs), `fetchQuery`, `useMutation` and `commitMutation`. Documents are read from `gql` / `graphql` tags (fragment interpolations included), codegen's client preset `graphql()`, codegen's generated documents and imported `.graphql` files. `useFragment` records which components read which fragment.
- **GraphQL types**, in this order: type arguments at the call (`useQuery<Data, Vars>`), codegen's `TypedDocumentNode`, the Relay compiler's `$data` / `$variables` (masked fragment data is merged back in, so the type matches what the server sends), then the schema: a local schema file (config `graphql.schema`, or found from `relay.config.json`, the codegen config or `schema.graphql`), else **live introspection** of an endpoint (config `graphql.introspection`, header values from env variables, fetched on `dev` and `scan` and cached in `.flow-checker/cache/`). Documents that don't fit the schema are flagged. The client setup gives the endpoint (`new ApolloClient()`, `HttpLink` / `BatchHttpLink`, urql's `createClient()`, Relay's `Network.create()`), batching, persisted queries and GET queries. Apollo's `refetchQueries: ['Todos']` and `client.refetchQueries()` are cache links to the queries by operation name.
- **GraphQL capture.** Captures carry their operation (from `operationName`, the query text, or the GET query); batched requests are split into one capture per operation with its own result; persisted queries (Apollo's APQ, Relay / codegen document ids) are mapped to their operation by the hash of the document or a persisted query manifest (config `graphql.persistedQueries`, or found by name). Matching uses the operation (new `GraphQL operation` evidence), and type checks compare `variables` and `data` (fields clients add, `__typename` and Relay's `id`, aren't counted as extra). New `GraphQL` section on the overview, a GraphQL row on requests and captures, `graphql.md` in the Markdown export, a `doctor` check.
- Postman collections: GraphQL requests (GraphQL mode, `graphql-request` in v3 folders, or a JSON body with a `query`) are matched to sites by operation, and their example `data` gives types.
- **Server-sent events.** `new EventSource(url)` and streamed `fetch` (an `Accept: text/event-stream` header, or a fetch of a route handler that answers with an event stream) are request sites with transport `sse`. The scan lists the events each one listens to (`onmessage`, `addEventListener(name)`, also on refs and with listener functions declared elsewhere) and the type its data is read as (`JSON.parse(e.data) as T`, a typed variable, `Schema.parse(...)`, `MessageEvent<T>`). Route handlers that answer with `text/event-stream` are read for the events they write (`event:` / `data:` text, also through helpers such as `send('tick', data)`, imported or not); events the client has no type for take the handler's, and events nobody listens to are shown as such. New `Event streams` section on the overview and README of the Markdown export, an events list on requests and an event stream section on route handler pages.
- **Event stream capture.** In the browser, `EventSource` is wrapped and streamed `fetch` responses are read through a copy; on the server, upstream event streams are read the same way. Each message (event name, id, time, size and data, redacted like bodies) is recorded; the capture is sent when the stream opens and updated with new messages every second until it ends. New options `capture.maxMessages` (default 200 per connection) and `capture.maxMessageBytes` (default 64 000; larger messages keep only their size). Captures are matched with new `event stream` evidence (the API and the event names received) and type-checked per event; a message that doesn't fit its event's type flags the request. The dashboard shows a message timeline on each stream capture.
- **WebSockets.** `new WebSocket(url, protocols)` and socket.io's `io(url, options)` are request sites with transport `websocket`. The scan lists the messages each one sends and receives with their types: native sockets' `onmessage` / `addEventListener('message')` (read like EventSource listeners) and `send(JSON.stringify(x))`; socket.io's `on(name)` / `once(name)` and `emit(name, data)`, typed from the listener parameter, the value sent, or typed events (`Socket<ServerEvents, ClientEvents>`). Sockets kept in a ref and used from event handlers, or opened in a helper, are followed. socket.io's URL is `<origin>/socket.io/` (or `options.path`), and a path in the URL is the namespace. New `WebSockets` section on the overview and in the Markdown README, and a messages list on requests.
- **WebSocket capture.** In the browser, `WebSocket` is wrapped: each message sent and received is recorded (direction, time, size and data, redacted like bodies; binary messages keep only their size), with the subprotocol and the close code and reason. socket.io traffic is read from its frames: events become named messages with their arguments, while pings, the handshake and acks are left out, and its HTTP long-polling requests are no longer captured. Captures are sent when the socket opens and updated every second, within `capture.maxMessages` and `capture.maxMessageBytes`. Matching uses new `WebSocket` evidence (native or socket.io, and the socket.io event names), and each message is type-checked against its direction and name; a sent message that doesn't fit is flagged as such. The message timeline marks each message sent or received. Sockets opened by dev tools that inject code into the page (such as Console Ninja) are ignored.
- React Query keys are no longer lost on requests a query sends right after the page renders (seen on Next.js 15 about one load in three): the runtime looks for the QueryClient again on each new request until it finds it.
- Faster request scan: calls to functions declared in `.d.ts` files (such as `fetch`) no longer search the whole declaration file for an implementation. On a 1,800-file app this saves about a second per scan.
- `.flow-checker/model.json` is now version 8. Version 1–7 files still load.

## 0.1.0

First public release.

- **Scan** of Next.js App Router projects (13.4+): routes, layouts, component trees with server/client boundaries, request sites (`fetch`, axios, wrapper clients, React Query, SWR, Server Actions, route handlers with their second hop), fully resolved types, navigation and inferred user flows.
- **Dashboard** (`flow-checker`): overview with a to-do list of flags, route map (graph and tree), page and component views, flows, live captures, types index and export.
- **Capture** while you test, in the browser and on the server, redacted by default before anything is saved.
- **Verification:** captures matched to the code that sent them, type comparison of captured bodies against the declared types, and flows confirmed by walking them.
- **Watch mode:** incremental re-scans in a worker thread, with `needs re-check` on requests whose code changed.
- **Export:** Markdown docs with Mermaid diagrams, and a static read-only copy of the dashboard.
- **Config:** `root`, `appDir`, `devCommand`, `ports`, `include`/`exclude` (file globs; tests, stories and mocks skipped by default), `apiClients` (HTTP libraries and API client packages whose calls are requests), `capture`, `types.maxDepth` and `export`. `flow-checker init` writes the defaults into the new config file.
- **`flow-checker doctor`** checks Node, Next.js, hooks, tsconfig, ports and `.gitignore`.
- **`withFlowChecker()`** (`@integr8-media/flow-checker/next`) makes the capture hooks work on Next.js 13.4–15.2.
